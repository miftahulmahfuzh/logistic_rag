# Plan: a larger, less Kirana-like holdout (implemented 2026-10-29: see eval/ITERATIONS.md, "Holdout v2")

Why: the current holdout has 10 chunks, so k=8 returns most of the document and retrieval changes cannot show up in answers. It also
resembles Kirana (same author, similar structure). Generalization is the priority: the recruiter's demo is an unseen document.
Rules from iteration 3 still apply: nothing document-specific in `src/`, fix settings before looking at results, questions frozen after commit,
holdout never used to pick a setting, honest numbers, no API key or PDFs in git.

## 1. Document (generated by `scripts/make_holdout2_pdf.py`, not committed as PDF)
- A third fictional company in a different industry and register (for example a regional hospital group or a water utility), 25 to 40 pages, targeting 60+ chunks.
- Structure deliberately unlike Kirana: two-column prose pages, a table of contents, long notes-to-the-accounts style prose, footnotes, a glossary,
  a table that spans three pages, a table with merged header cells, a table without ruling lines, two charts, one scanned page (image of text), one page rotated or landscape.
- Mixed spelling (UK and US in different sections), numbers in several formats (1,234.5, 1.234,5 in one table, percentages, ranges), repeated near-identical rows across years.

## 2. Questions (about 25, written before any run)
Lookup, table cell, calculation, synonym/paraphrase (no shared words), conceptual, multi-chunk, cross-reference to a missing appendix, near-miss unanswerable (4),
false premise (2), conflict (1), chart (2), scan (1). Gold pages and gold chunks. Status `HOLDOUT2`, frozen at the commit that adds them.

## 3. Use
1. Generate, ingest, run the current code (`holdout2_baseline`). Expected pitfalls to record, not fix: three-page table merge, multi-column reading order.
2. Retrieval-only ablation on all four question sets: normalisation `none|spelling|full` x retriever `bm25|hybrid`.
3. Pre-register the decision rule before running: a setting is kept only if it does not worsen mean first-gold-chunk rank on the Kirana sets and on **both** holdouts.
4. Report rank metrics and answer metrics side by side; at 60+ chunks and k=8, answer-level effects of retrieval should become visible.

## 4. Pros and cons
- Pros: retrieval changes can move answers; it breaks assumptions the code might have absorbed from Kirana (single column, ruled tables); it settles the open Snowball question with more than two documents.
- Cons: more generation effort; about 5 or more vision calls to ingest plus cache; still synthetic and written by the same author as the code; ingestion failures may dominate and mask retrieval effects.

## 5. Out of scope here
Fixing any ingestion weakness the new document exposes (record it in a failure analysis, plan it separately); real third-party documents (licensing, labelling effort).
